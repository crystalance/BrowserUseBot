0. Two things we are designing

#FeatureOne-line goal
1 Long-horizon 面经 harvester One task = one company. The agent behaves like a human: searches, opens post after post, remembers what it already visited, and organizes dozens–hundreds of interview posts into a Markdown file saved on the server — running as long as needed, but efficiently.
2 Request-ID & trace correlation On /new, immediately return a short request id. That id ties every LLM call of the task together in Langfuse so you can jump from a Telegram message straight to the trace.

They connect: the request id becomes the Langfuse session id that groups all the (chunked) traces a long harvest produces — search one id, see the whole job. We design #2 first because #1 depends on it.

1. Feature 2 first — Request ID & Langfuse correlation

1.1 Problem

Today start_run_trace(goal) in core/observability.py creates a Langfuse trace with a server-generated id we never surface. When a task misbehaves you cannot find its trace without guessing by timestamp. We need a stable id, generated before the run, shown to the user, and attached to every trace/generation.

1.2 Design

PieceDecision
ID formatreq-YYYYMMDD-xxxxxx (date + 6 base32 chars from secrets.token_hex). Human-readable, sortable, collision-safe for our volume. Generated in a new core/ids.py :: new_request_id().
Where generatedIn the Telegram gateway cmd_new, the instant a task is accepted — so it can be echoed to the user before the browser even starts.
Langfuse bindingPass request_id into start_run_trace. Set it as the trace id (Langfuse v2 client.trace(id=..., session_id=..., tags=[...]) accepts a client-supplied id) AND as session_id AND as a tag. Triple-binding = findable by URL, by session grouping, or by tag search.
Deep linkIf LANGFUSE_PROJECT_ID is set, build {LANGFUSE_HOST}/project/{pid}/traces/{request_id} and send it in the reply. Otherwise tell the user to search the id (still one click in Langfuse).
Local correlationAdd a request_id column to RunStore (core/store.py) and use it as the transcript filename (run-{request_id}.json) so Telegram → Langfuse → SQLite → transcript all share one key.

2. Feature 1 — the long-horizon harvester

2.1 What makes this hard

ChallengeWhy the current one-shot loop fails
Volume (dozens–hundreds of posts)A single Agent.run() accumulates every step's DOM + reasoning in the message history. At ~12–16k input tokens/step (measured), 100+ steps means an ever-growing, slowing, eventually context-overflowing run.
No memory of visited postsThe agent re-opens the same cards after scrolling; wasted steps, duplicate records. Nothing survives a crash or a second run.
Not resumableIf step 90 fails, all progress is trapped in volatile history. We want "continue Google from where we stopped."
Final answer too bigThe Phase-2 synthesize() currently sends every record in one prompt — fine for 15, not for 200.

2.2 Core idea — decouple the crawl from the LLM context

Two mechanisms do the heavy lifting; both push state out of the volatile agent history into durable stores:

Mechanism A

Persistent Visited-Ledger

A per-company SQLite ledger of every post id we've seen and its outcome. Dedup is enforced inside the tool, not in the prompt — the agent never needs to be told "here are the 140 ids you already did."

Mechanism B

Chunked fresh-agent runs

An outer orchestrator runs the agent in bounded chunks (e.g. ~15 new posts / ~25 steps each). After a chunk, we discard the history and start a fresh agent with a tiny brief. Constant context, resumable, unbounded total reach.

2.3 The Visited-Ledger (core/ledger.py — new)

Canonical key = the note id parsed from the URL (/explore/<id> or /search_result/<id>).

CREATE TABLE visited (
    company   TEXT NOT NULL,     -- "google"
    note_id   TEXT NOT NULL,     -- canonical id from URL
    url       TEXT,
    title     TEXT,
    status    TEXT NOT NULL,     -- saved | empty | failed | skipped
    ts        REAL NOT NULL,
    PRIMARY KEY (company, note_id)
);

A second table in the same SQLite file is the durable candidate queue — the discovery output, so a fresh chunk can resume by opening URLs directly instead of re-scrolling:

CREATE TABLE candidates (
    company   TEXT NOT NULL,
    note_id   TEXT NOT NULL,     -- canonical id
    href      TEXT NOT NULL,     -- full url WITH xsec_token (openable directly)
    title     TEXT,
    added_ts  REAL NOT NULL,
    PRIMARY KEY (company, note_id)
);
-- "remaining work" = candidates LEFT JOIN visited WHERE visited.note_id IS NULL
  • Dedup: extract_and_save becomes ledger-aware — it computes the note id from the record's url, and if the ledger already has it saved, it returns "duplicate, skipped" and does not re-save. The agent can happily re-encounter cards; convergence is automatic.
  • Resume: a new task for the same company loads the ledger; already-saved ids are skipped, so the crawl naturally continues with fresh posts.
  • Health: empty/failed statuses let us retry-or-skip flaky posts and report a real success rate.
Key design win: dedup lives in the tool + ledger, so the LLM prompt stays small no matter how many posts we've done. This is what makes hundreds-of-posts feasible.

2.4 Chunked orchestration (core/harvest.py — new)

HarvestOrchestrator.run(company, request_id):
  ledger = VisitedLedger(company);  store = CollectedStore(company)
  chunk = 0
  while ledger.saved_count() < company.target and chunk < MAX_CHUNKS:
    chunk += 1
    brief = build_chunk_brief(company, saved=ledger.saved_count(), target=company.target)
    # FRESH agent, bounded steps, SAME browser session (keeps login+scroll pos)
    before = ledger.saved_count()
    await run_chunk(brief, session_id=request_id, chunk_no=chunk,
                 max_steps=CHUNK_STEPS, tools=ledger_aware_tools(ledger, store))
    heartbeat(request_id, ledger)  # 📈 Telegram progress
    if ledger.saved_count() == before: break  # no-progress guard → stop, don't loop forever
  md = organize_to_markdown(company, store)  # chunked synthesizer
  MdWriter.save(company, md)  # workspace/harvest/<company>/面经.md
DecisionRationale
Fresh agent per chunk, shared BrowserSessionResets the LLM message history (bounded context / cost) while keeping the logged-in browser, cookies, and scroll position — so the crawl continues seamlessly.
Chunk brief carries counts, not lists"You've saved 45/100. Keep opening unseen posts; duplicates auto-skip." No giant id list in the prompt.
No-progress guardIf a chunk saves 0 new posts (exhausted results / blocked), stop cleanly instead of burning chunks.
MAX_CHUNKS ceilingSafety cap on total work even though "time doesn't matter."

2.5 Resume — how does a fresh chunk know where to start?

A fresh agent has zero memory of prior chunks. It resumes only because progress lives in durable stores outside the discarded message history. Three layers, weakest to strongest:

LayerWhat it gives the fresh chunkReliability
Shared BrowserSessionSame logged-in browser, same results page & scroll positionFragile — 小红书's infinite feed virtualizes / re-ranks on interaction, so scroll position is not a dependable cursor
Durable candidate queue (new)The remaining unvisited hrefs (with xsec_token); the chunk opens each by URLDeterministic — independent of scroll / feed order
Visited ledger + tool dedupRe-opening a seen card is a no-op (extract_and_save auto-skips)Makes imperfect positioning harmless — never duplicates
Resume rule: a chunk first drains the candidate queue by opening URLs directly (deterministic), and only scrolls to discover more candidates when the queue is empty. So "where to start" = the next unvisited row in candidates, not "wherever the browser happened to be scrolled."

The chunk brief therefore reads roughly: "Company Google. Saved 45/80. Here are the next N unvisited post URLs — open each, extract_and_save, close. Duplicates auto-skip. When this batch is done and you need more, scroll the search results and harvest new cards." — counts and a short URL batch, never the full history.

2.6 Per-chunk agent behavior (human-like, efficient)

  1. Drain the queue first: take the next batch of unvisited candidates and open each by URL (deterministic resume) — click/navigate to open the detail, then one extract_and_save whose JS returns {note_id, url, title, body, meta}. Ledger auto-dedups. Close (Esc). Repeat.
  2. Discover more only when the queue drains: one run_js harvests the visible result cards → [{note_id, title, href}]; scroll 1–2× and re-harvest. New rows are appended to candidates for this and future chunks. (Bulk, one LLM call.)
  3. Stop when the chunk hits CHUNK_STEPS or its new-post target; the orchestrator takes over.
Everything repetitive is already CodeAct (run_js / extract_and_save in core/tools.py), so the LLM spends tokens on navigation decisions, not on transcribing text. Screenshots are already disabled when vision is off (_disable_screenshots), removing per-step capture overhead.

2.7 Incremental Markdown output (core/mdwriter.py — new)

Storage layout on the server:

workspace/harvest/
  google/
    面经.md              <- organized, human-readable final doc
    raw.jsonl            <- every saved record (CollectedStore, append-only)
    ledger.sqlite        <- visited ids + candidate queue (dedup/resume)

  amazon/
    …
  • Crash-safe: raw.jsonl is appended per post, so a failure keeps all prior progress; the 面经.md is (re)generated from it at each checkpoint.
  • Chunked synthesis: organize_to_markdown maps records → grouped sections (by role / round / year), summarizing in batches of ~20 then merging — an extension of the existing synthesize() so it scales past a single prompt.
  • Retrieval later: a flat, predictable path per company. (Fetching these off the server — /get <company> over Telegram, or a small static endpoint — is a follow-up, out of scope here.)

2.8 New skill (skills/company-interview-harvest.md)

Follows the existing SkillStore format. Triggers on 面经/interview + a company name; sets Allowed-Hosts/Login-Hosts. Instructs the collect-then-organize loop above and tells the agent duplicates auto-skip so it should keep exploring rather than stopping early.

Skill-routing fix (from the bugs log, item 3): matching must require an intent word (面经/interview/面试), not just a site name like 小红书, so ordinary "get my latest post" tasks don't get the harvester prepended. Tighten Skill.score() to weight intent triggers.

2.10 Is this 小红书-only? — site-agnostic engine + thin source adapters

No — only a thin adapter is site-specific. Everything that makes the long-horizon crawl work operates on abstract {note_id, url, title, body} records and is reusable across sources. The per-site part is small and isolated.

ComponentSite-agnostic?Site-specific part (if any)
Request id / Langfuse tracingYes—
Visited ledger + dedupYesparsing a canonical note_id from a URL
Candidate queueYesthe href/token URL shape
Chunked orchestratorYes—
MdWriter + chunked synthesizerYes—
Harvest recipe (search flow, discover JS, extract JS, selectors)Noall of it — this is the adapter

Formalize the per-site part as a SourceAdapter (core/sources/base.py — new) so the generic orchestrator can drive any site:

class SourceAdapter(Protocol):
    key: str                       # "xiaohongshu"
    allowed_hosts: list[str]
    login_hosts: list[str]
    def search_entry(self, query: str) -> str        # URL / how to run the search
    def parse_note_id(self, url: str) -> str | None   # canonical id
    discover_js: str               # run_js: harvest visible cards -> [{note_id,title,href}]
    extract_js: str                # extract_and_save: one post -> {note_id,url,title,body,meta}
    def post_date(self, record: dict) -> float | None # for incremental (2.11); optional
  • First adapter = xiaohongshu (lifts today's skills/xiaohongshu-search.md JS into code).
  • Later adapters (一亩三分地 / Blind / LeetCode discuss) are ~50 lines each; the ledger, queue, chunking, md, and tracing are untouched.
  • companies.json can name which source(s) a company should be harvested from.
Answer: the solution is a generic harvesting engine + a 小红书 adapter. It is not locked to rednote; multi-site is a matter of adding adapters, not re-architecting.

2.11 Daily incremental crawl — pre-design so it's cheap to build later

Goal you flagged for later: "search for new posts daily." Because dedup + ledger already exist, daily deltas need almost no new machinery — we just pre-wire two hooks now:

Hook (add now)Why it makes daily trivial later
meta.json: last_run + high-water mark (newest note_id/date seen)Lets a run know "anything past this is already mine."
run(company, *, mode="full"|"incremental", since=None) on the orchestrator + run_taskDaily = flip mode="incremental"; no signature change later.
Adapter post_date() + a "sort by newest" search entryDiscovery can early-exit once it reaches posts older than last_run — a cheap delta, not a full re-crawl.
  • Incremental loop: search sorted by 最新 → queue only note_ids not in visited → stop when post_date < last_run (or after K consecutive already-visited cards, which the ledger gives for free when dates are missing).
  • Output: new records append to raw.jsonl; 面经.md is regenerated (or a "newly added" section appended) and meta.json advanced.
  • Scheduler: a small APScheduler/cron fires HarvestOrchestrator(company, mode="incremental") per company daily. That's the only genuinely new piece — everything it calls already exists.
Pre-design cost today = accept a mode/since arg and write meta.json. We don't build the scheduler now, but nothing will need reshaping when we do.

  │  rid = req-20260714-9fa3c1  (Feature 2)
  ▼
HarvestOrchestrator.run(google, rid)  (Feature 1)
  ├─ chunk 1 → Langfuse trace (session_id = rid)  → 15 saved
  ├─ chunk 2 → Langfuse trace (session_id = rid)  → +14 saved (3 dup skipped)
  ├─ …
  └─ organize → google/面经.md
Search rid in Langfuse → the whole multi-chunk job, grouped as one session.

Each chunk is its own trace (bounded, easy to read), but they share session_id = request_id, so Langfuse's session view reconstructs the entire long-horizon task under the one id you were handed on Telegram.

6. Open questions

  • Source site(s): start with 小红书 only, or also 一亩三分地 / LeetCode discuss / Blind? Each is a ~50-line SourceAdapter (§2.10); the ledger/orchestrator are source-agnostic.
  • xsec_token expiry: the candidate queue stores hrefs with a xsec_token that can expire, so open-by-URL may fail on an old queue. Options: (a) store note_id only and re-resolve the token at open time by re-harvesting the card; (b) on an open failure, fall back to click-from-list (resume Layer 1) — dedup keeps it correct either way; (c) treat a stale queue as "needs a fresh discovery pass." Decide the token TTL policy.
  • Daily incremental (§2.11): confirm the delta stop-rule — by post_date < last_run, or by K consecutive already-visited cards when dates are unavailable? And append-vs-regenerate for 面经.md.
  • Target count vs. "all": per-company target cap, or crawl until no new results? No-progress guard supports "until exhausted."
  • Freshness: re-run cadence — see the daily incremental pre-design in §2.11 (mode="incremental", meta.json.last_run).
  • One company per task confirmed; do we want a /new all that queues the whole company list sequentially?
  • Login handoff mid-harvest: if a chunk hits a login wall, the existing noVNC handoff pauses that chunk — fine, but the heartbeat should surface it.
