BrowserUseBot — Observability Design

Goal: see where every run spends time, tokens, and $; catch failures (429 / JSON / timeouts); self-hosted on AWS EC2, viewed from a laptop browser.

1. What we need to observe

LayerSignalsWhy
LLM callmodel, prompt/completion tokens, latency, cost, finish_reason, errors (429, trailing-JSON, 75s timeout)The dominant cost & latency driver — this is where the ~45min went
Agent stepstep #, action(s) taken (run_js/click/save_items…), duration, retriesFind wasted steps / loops / tab churn
Task rungoal, ok, #steps, needed_human, #collected records, end-to-end latencyProduct-level success & throughput
Browser/CDPnavigation, screenshot-capture timeouts, run_js exec timeSite-side slowness

We already emit much of this to logs + workspace/logs/transcripts/*.json + the SQLite run store. Observability = structure it, trace it, and put it behind a UI.

1b. Chosen approach — local-dev, Docker Compose, portable

Decision: run the observability stack locally for development (not on the cloud yet). Priorities: easy to deploy and portable across dev machines (Windows now → MacBook later). Resources are not a concern on a dev laptop.
  • Mechanism = Docker Compose. Commit a docker-compose.yml; on any machine with Docker Desktop it's just docker compose up -d. Identical on Windows and macOS → trivially portable when you switch environments.
  • Tool = Langfuse (self-hosted via its official compose) — LLM-native traces + cost / latency / token dashboards, which is exactly what we need to attack the ~45-min problem. (Since resources aren't a concern locally, its multi-container stack is fine.)
  • Bot points at it via env (LANGFUSE_HOST=http://localhost:3000 + keys). The same instrumentation code later works against a cloud/self-hosted host by only changing the env — cloud deploy stays an option, not a requirement.
  • Switching machines = install Docker Desktop, git clone, docker compose up -d, restore .env. That's it.

3. Stack options

Recommended stack (resume-strong, pragmatic):
  • Core Langfuse (self-hosted) — every LLM call as a generation (tokens, latency, cost, model), grouped into a trace per task run, with step spans. This is the LLM-observability centerpiece.
  • Optional Prometheus + Grafana — counters/histograms for success_rate, steps/run, p50/p95 latency, tokens, 429s → one dashboard.
  • If EC2 RAM is tight (≤4GB): use Arize Phoenix (single container) instead of Langfuse.

4. Instrumentation plan (where in the code)

  • LLM layer — wrap the chat model built in core/llm.py: on each ainvoke, record a Langfuse generation (model, input/output tokens from usage, latency, error type). browser-use exposes token usage on its completion object, so we capture it there.
  • Run layer — in core/runner.py, open a Langfuse trace per run_task (goal, run_id) and child spans for Phase-1 (collector) and Phase-2 (synthesizer).
  • Step layer — via the existing on_step_start hook + transcript, emit a span per agent step (actions, duration).
  • Metrics — a tiny Prometheus exporter reads the SQLite run store + counters (increment on 429/timeout/json-error) and exposes /metrics.
  • Env-gated — all tracing behind OBSERVABILITY=langfuse + keys, so local dev stays simple and prod turns it on.

5. Deploy on EC2 & view from your laptop (your question)

Yes — fully doable. The stack runs as Docker containers on the EC2; you reach the web UIs from your laptop by one of three methods (most→least secure):

A. SSH tunnel recommended — nothing exposed

ssh -L 3000:localhost:3000 -L 3001:localhost:3001 ubuntu@<EC2-IP>
# then on your laptop:  http://localhost:3000  (Langfuse)   http://localhost:3001 (Grafana)

No security-group ports opened; the UIs bind to localhost on the box and travel through your existing SSH. Best default.

B. Security-group port (quick, like the noVNC link)

  • Open inbound 3000 (and 3001) to your IP only in the security group.
  • Browse http://<EC2-IP>:3000. Simple, but the UI is internet-facing — keep it IP-restricted and set a strong Langfuse admin password.

C. Reverse proxy + TLS + auth production

  • nginx/Caddy in front → HTTPS (Let's Encrypt) + basic-auth, one domain. Do this if it ever becomes multi-user or always-on.

Resource note — your box is c7i-flex.large (2 vCPU / 4 GB)

4 GB is already tight when Chromium runs (OOM risk). Do NOT co-host a heavy Langfuse v3 stack (Postgres+ClickHouse+Redis+MinIO, ~3–4 GB) on the bot box — it would starve/kill the browser mid-run. Choose one of these instead:

PathWhere observability runsCost / riskResume signal
1. Separate observability node (recommended)A 2nd small EC2 (e.g. t4g.small ~2 GB) runs Langfuse; the bot sends traces over the network~a few $/mo (stop when idle); bot box stays safeStrong — "separated the app plane from the observability plane"
2. Langfuse Cloud (free tier)Managed; bot only runs the SDK$0, zero infraGood — but less "I deployed infra"
3. Phoenix on the same boxSingle ~500 MB container beside the botCheapest but adds memory pressure; watch for OOMOK for a light demo

Key insight: the instrumentation code in the bot is identical for all three — only the endpoint/keys differ. So: build the SDK instrumentation once (env-gated, host configurable), validate instantly against Langfuse Cloud free tier, then later self-host Langfuse on a separate small EC2 by just changing LANGFUSE_HOST. Best of both: fast start now, infra story later.

Access from laptop stays the same — SSH-tunnel into whichever node runs the UI (§5A).

Original resource guidance

Langfuse v3 full stack (Postgres+ClickHouse+Redis+MinIO) wants ~3–4GB free RAM. On a 4GB box it's tight alongside Chromium — either (a) run observability on a separate small instance, (b) use Phoenix (single container, ~500MB), or (c) point the bot at Langfuse Cloud (managed) and skip self-hosting. For a resume, self-hosting on EC2 shows more.

6. Rollout steps

  1. Pick core: Langfuse (self-host) or Phoenix (lighter).
  2. docker compose up the observability stack on EC2; verify UI via SSH tunnel.
  3. Add the LLM-layer instrumentation (traces/generations) behind OBSERVABILITY env.
  4. Add run/step spans in the runner.
  5. (Optional) Prometheus exporter + Grafana dashboard for success_rate / latency / 429s.
  6. Run a task → confirm the trace shows per-step tokens/latency/cost and pinpoints the 75s timeouts.
